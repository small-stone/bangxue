# Design

## Context

见 `proposal.md`。当前 `apps/api` 只有健康检查和 Agent 占位；判分与出题图尚未实现。`REQUIREMENTS.md` 仍写「视觉模型识别 → 对照答案判分」，没有 Jev。

Jev（TypeSafe System One）不生成字符串、不接收图片。调用方提交 state 和预定义问题，取回 Choice / Score 一类结果和概率。因此它接在识图和草稿生成之后，不替换 OpenAI / Claude。

## Goals / Non-Goals

**Goals:**

- 单一 Jev 客户端，供判分与两条出题路径复用
- 判断问题在代码里预定义，输出可直接分支，不解析自由文本
- 低置信度只影响展示与追问，不绕过家长确认

**Non-Goals:**

- 本期不实现完整出题、RAG、PDF 或成绩表（那些仍是后续 change；本设计只定 Jev 的接入点）
- 不用 Jev 做模型路由或替换 Claude / OpenAI
- 不把 Jev 做成独立部署单元
- 不在置信度很高时自动确认成绩

## Decisions

### 1. 调用位置

```
方式 B：对话状态 → Jev(信息是否足够)
                 ├─ 否 → 追问（不生成）
                 └─ 是 → LLM 出题 → 家长确认 → PDF

方式 A：选题/范围 → RAG + LLM 出题 → Jev(是否在范围内)
                                    ├─ 有越界 → 标出，家长决定重出或剔除
                                    └─ 在范围内 → 家长确认 → PDF

判分：图片 → Vision 识别 → Jev(重拍?) → Jev(每题对错+置信度)
                         → 主观题评语仍走 LLM → 家长确认 → 写库
```

- **选择**：Jev 作为 `agents/shared` 里的判断客户端，由方式 A 图、方式 B harness、判分子图调用
- **备选**：每个路径各写一套 HTTP 调用 — 拒绝，密钥与重试会分叉
- **备选**：用 LLM 结构化输出代替 Jev — 拒绝，与本次需求相反

### 2. 问题预定义，不让 Jev 自由发挥

判分问题示例（实现时用 TypeSafe 的类型化问题，而不是聊天 prompt）：

- 图像是否应重拍（是/否）
- 该题相对标准答案（正确/错误）

流程问题示例：

- 当前对话是否足够出题（是/否）；若否，缺的是题量、知识点还是科目（封闭枚举）
- 该题是否落在所选教材范围内（是/否）

置信度低于约定阈值时：判分题标记「需留意」；流程判断倾向更保守的分支（追问或标出越界）。阈值放在配置，不写死在提示词里。

### 3. 密钥与失败

- 环境变量注入 API key，不入库
- Jev 超时或 5xx：判分路径把该题标为「判断失败、请家长核对」，不假装已判对；流程路径改为追问或提示「暂时无法自动检查范围」，不静默放行越界题
- Jev 单次调用预期为亚秒到约一秒级，不单独开 SSE；外层识图/出题的进度反馈保持不变

### 4. 与现有文档的关系

实现时更新 `REQUIREMENTS.md` 第 2.3 节判分、方式 B 追问、方式 A 确认，以及技术栈表中的模型行。`openspec/config.yaml` 的 context 补一句 Jev 职责，避免后续规划又把判分全部交给 Vision LLM。

## Risks / Trade-offs

- **[Risk] Jev 对中文教学习题的判断不稳定** → 低置信度与失败都回到家长确认；先用客观题验证，主观题评语不依赖它
- **[Risk] 早期访问 API 不稳定或需 waitlist** → 客户端可替换；本地缺少 key 时明确报配置错误，不用随机对错冒充
- **[Trade-off] 多一次网络往返** → 相对完整 LLM 判分更短；识图仍是判分耗时的大头

## Migration Plan

- 尚无线上判分数据，无迁移
- 文档与代码同时引入；未配置 key 时相关接口返回明确错误，不影响现有 `/health`

## Open Questions

- TypeSafe 具体 SDK 与问题 schema 以接入时的官方文档为准（不改变上述判断种类）
- 置信度阈值的具体数字在有样例题之后再标定，不在本 change 写死
